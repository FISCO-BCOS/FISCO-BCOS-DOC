# FISCO BCOS Web3 钱包开发
作者：肖自信｜四川领链科技有限公司

## 背景

FISCO BCOS 已经具备成熟的联盟链能力，但 DApp 用户要像使用 MetaMask 一样，在浏览器中完成账户授权、交易确认和本地签名，仍然存在明显的兼容断层。

这个断层主要来自三个问题：**节点使用哪一种 RPC 协议**、**链使用哪一种密码体系**，以及**传统 SDK 的运行环境与浏览器安全模型并不相同**。

### 1. FISCO BCOS 3.9.0 以前没有 Web3 JSON-RPC

FISCO BCOS 官方从 3.9.0 开始提供 Web3 JSON-RPC，并增加 `web3_chain_id` 和 `[web3_rpc]` 配置。在此之前，DApp 只能使用 FISCO BCOS 原生 RPC；即使节点已经升级到 3.9.0 或更高版本，Web3 RPC 也默认关闭，需要运维人员主动配置和开启。

这意味着 MetaMask、Hardhat 等依赖 `eth_*` 接口和以太坊交易格式的工具，不能直接覆盖旧版本节点、未开启 Web3 RPC 的节点，以及仍在使用原生 RPC 的既有业务。

参考：[FISCO BCOS v3.9.0 版本说明](https://fisco-bcos-doc.readthedocs.io/zh-cn/latest/docs/introduction/change_log/3_9_0.html)、[使用 Web3 工具部署调用合约](https://fisco-bcos-doc.readthedocs.io/zh-cn/latest/docs/develop/web3_usage.html)。

### 2. Web3 兼容不等于国密兼容

FISCO BCOS 的 Web3 兼容通道面向以太坊工具链，交易采用以太坊式 RLP/EIP-155 语义，对应标准密码体系的 secp256k1 签名和 Keccak-256 哈希。

国密链的交易规则不同：账户和签名使用 SM2，摘要使用 SM3，签名字段还需要携带公钥。官方资料也明确说明，标准版与国密版在签名算法、摘要算法和交易签名数据长度上均有差异。因此，能够连接 Web3 JSON-RPC，并不代表以太坊钱包生成的交易可以直接用于国密链。

本项目将这一限制明确为：**Web3 模式只用于标准密码体系；国密链使用 FISCO BCOS 原生 RPC 和原生交易格式。** 这不是把 SM2/SM3 硬塞进以太坊交易，而是在钱包内部选择正确的协议和密码实现。

参考：[FISCO BCOS 国密支持方案](https://fisco-bcos-doc.readthedocs.io/zh-cn/release-3.6.0/docs/design/guomi.html)。

### 3. 传统原生接入依赖 SDK 运行环境，浏览器不能直接运行 Java

FISCO BCOS 原生 RPC 协议在传统项目中，原生交易构造、TARS 编码、国密签名以及节点通信通常由 FISCO BCOS Java SDK 或控制台完成。因此，很多现有接入方案实际上依赖 JVM、Java 密码库和 SDK 配置。

浏览器页面和 Chromium 扩展不能直接启动 JVM，也不能把 Java SDK 当作普通前端依赖运行。最直接的替代办法是在服务器部署 Java 签名服务，由浏览器把交易请求交给后端处理，但这会产生一个更严重的问题：如果后端负责签名，用户就必须上传私钥，或者把私钥长期托管在服务器上。

这与钱包应有的安全边界相冲突。我们希望做到：

- 用户自己生成、备份和保管助记词与私钥；
- 私钥只存在于用户浏览器扩展的加密存储和短暂解锁内存中；
- DApp 和业务后端都不能读取私钥；
- 节点只接收已经签名的原始交易，不参与用户密钥托管。

因此，本项目不能简单地在浏览器前面增加一个“Java 代签后端”，而需要在浏览器端实现钱包真正需要的那部分原生 SDK 能力。

需要说明的是，本文后续提到的 `RPC代理` 并不是代签后端，也不是钱包的核心安全边界。它的定位是一个开发、演示和受控测试环境下的配套连链模板：帮助浏览器插件通过 HTTP JSON-RPC 访问 FISCO BCOS Java SDK 能连接的节点，同时继续保持“钱包本地签名、私钥不出扩展”的设计原则。

## 我们要解决什么问题

如果只使用通用以太坊钱包，会留下两个空白：

- 无法连接 3.9.0 以前或没有开启 Web3 RPC 的 FISCO BCOS 节点；
- 无法按照 FISCO BCOS 国密规则生成 SM2/SM3 原生交易。

如果只使用传统 FISCO BCOS Java SDK，DApp 又缺少浏览器钱包常见的 Provider 注入、按站点授权、交易确认弹窗、账户切换和本地密钥托管体验；浏览器本身也无法直接运行 Java 代码。若改由中心化后端代签，又会让用户失去对私钥的直接控制。

因此，我们开发这个钱包的目标是提供一个连接 **Web3 DApp 交互方式** 与 **FISCO BCOS 多版本、多密码体系** 的兼容层。

## 本钱包如何做到

### 1. 对 DApp 提供统一 Provider

扩展向页面注入 EIP-1193 风格的 `window.fisco`。DApp 始终通过 `request({ method, params })` 与钱包交互，不直接接触私钥，也不需要直接连接节点。

钱包额外提供：

- `wallet_getMode`：返回当前是 `web3` 还是 `native` RPC；
- `wallet_getCrypto`：返回当前是 `standard` 还是 `gm` 密码体系；
- `wallet_getGroup`：在原生模式下返回当前 FISCO BCOS 群组。

这样，DApp 可以先做能力探测，再选择对应的合约编码和调用路径，而不是用节点版本号猜测能力。

### 2. 使用双 Adapter 屏蔽 RPC 差异

钱包内部根据网络配置选择两类适配器：

| 网络场景 | 钱包模式 | 处理方式 |
| --- | --- | --- |
| 3.9.0+，已开启 Web3 RPC，标准密码体系 | Web3 Adapter | 使用 `eth_*`、`net_*` 和 Web3 Chain ID |
| 3.9.0 以前或未开启 Web3 RPC，标准密码体系 | Native Adapter | 将公共 `eth_*` 请求映射为 FISCO BCOS 原生 RPC |
| 国密链 | Native Adapter | 使用原生 RPC，并构造 SM2/SM3 原生交易 |

例如，在原生模式下，`eth_blockNumber` 会映射为 `getBlockNumber`，`eth_call` 会映射为 `call`，签名后的交易则通过原生 `sendTransaction` 提交。RPC 适配只负责方法和结果转换，不接触私钥。

网络模式由用户明确选择，并在保存网络时实际探测端点：Web3 模式校验 `eth_chainId` 和 `eth_blockNumber`；原生模式校验群组列表和 `compatibility_version`。钱包不会仅凭“版本大于等于 3.9.0”就假定 Web3 RPC 已经开启。

### 3. 在浏览器端实现必要的原生 SDK 能力

本钱包没有尝试把完整 Java SDK 搬进浏览器，而是使用 TypeScript 和适合浏览器运行的密码库，实现发送交易所需的最小闭环：

1. 从原生 RPC 读取链 ID、群组 ID、区块高度、兼容版本和密码类型；
2. 在扩展后台构造 FISCO BCOS V0 交易数据；
3. 完成 TARS 编码、Keccak-256/SM3 摘要和 secp256k1/SM2 签名；
4. 在本地验证签名，并将签名、公钥等字段组装成原始交易；
5. 通过原生 `sendTransaction` 接口只提交已签名交易。

整个过程中，节点 RPC 端点只会看到公开账户地址、查询参数和签名后的交易。助记词、私钥以及 Vault 解密密钥都不会发送到节点、DApp 或业务服务器。

这种设计同时满足了两个目标：浏览器不依赖 Java 运行环境，也不需要用后端代签来牺牲用户的私钥控制权。

### 4. 使用两套交易编码与签名流程

钱包不会把所有交易强行编码成以太坊交易，而是根据当前模式选择正确的交易管线：

```text
DApp 发起 eth_sendTransaction
             |
             v
      钱包授权与确认弹窗
             |
       +-----+-----+
       |           |
       v           v
   Web3 模式    Native 模式
   RLP/EIP-155   FISCO V0/TARS
   Keccak-256    Keccak-256 或 SM3
   secp256k1     secp256k1 或 SM2
       |           |
       +-----+-----+
             |
      提交签名后的原始交易
```

- **Web3 标准交易**：本地补齐 nonce、gas price、gas limit 和 chain ID，使用 Keccak-256 计算摘要，以 secp256k1 生成 EIP-155 签名，再通过 `eth_sendRawTransaction` 提交；
- **FISCO 原生标准交易**：读取链 ID、群组 ID、区块高度和兼容版本，构造带 `blockLimit` 与安全随机 nonce 的 V0 交易，使用 Keccak-256 和 secp256k1 签名；
- **FISCO 原生国密交易**：使用 SM3 计算交易摘要，以 SM2 和 FISCO BCOS 约定的 user ID 完成签名与本地验签，并按原生格式附加签名公钥后提交。

交易提交后，钱包还会核对节点返回的交易哈希是否与本地签名结果一致，避免错误端点或异常响应被当作成功交易。

### 5. 同一份助记词支持标准与国密地址

钱包使用 BIP-39 助记词和统一的 BIP-32/BIP-44 派生路径：

```text
m/44'/60'/0'/0/{accountIndex}
```

同一个派生私钥会计算两套公开账户材料：

- 标准地址：`secp256k1 公钥 -> Keccak-256 -> 后 20 字节`；
- 国密地址：`SM2 公钥 -> SM3 -> 后 20 字节`。

切换网络或群组时，钱包只切换当前展示和使用的地址、哈希与签名算法，不改变助记词和派生路径。用户不需要为了标准链和国密链分别维护两套助记词。

### 6. 把兼容能力放进安全边界内

私钥始终留在扩展后台的加密 Vault 中。DApp 只能请求账户授权或发起交易，不能读取私钥。每次交易都经过来源校验、账户权限检查和确认弹窗，然后由钱包在本地签名。

钱包只注入 `window.fisco`，不会覆盖已有的 `window.ethereum`，因此可以与其他以太坊钱包共存。网络、账户或密码模式变化时，Provider 会向 DApp 广播状态变化，避免页面继续使用已经失效的上下文。

## 实现价值

这个钱包补全了 FISCO BCOS 浏览器端生态中的一段关键链路：

- 对旧节点和原生 RPC，提供接近 Web3 的 DApp 调用体验；
- 对 3.9.0+ 标准链，直接接入 Web3 JSON-RPC 生态；
- 对国密链，使用真正匹配 FISCO BCOS 的 SM2/SM3 地址与原生交易；
- 不要求用户安装 Java 环境，也不需要将私钥交给 Java 后端代签；
- 对用户，提供统一的助记词、账户管理、授权、确认和活动记录；
- 对 DApp，提供稳定的 Provider，而不要求业务代码持有私钥或理解所有底层交易格式。

简而言之：**FISCO BCOS 3.9.0 解决了标准链接入 Web3 工具的问题，而本钱包进一步解决了旧版/原生 RPC、国密交易、浏览器无法运行 Java SDK，以及用户私钥不能交由中心化后端保管的问题。**

## 当前支持边界

为了避免“兼容所有场景”的误解，当前实现仍有明确边界：

- Web3 模式仅支持标准密码体系和 legacy EIP-155 交易，暂不支持 EIP-1559 交易字段；
- 原生模式当前实现 FISCO BCOS V0 EVM 交易，暂不支持 WASM 群组交易；
- 国密能力应继续使用官方 SDK 测试向量和真实节点做交叉验证，并在生产发布前完成密码实现专项审计。
- 配套RPC代理当前定位为基础可运行模板，默认不包含完整认证、限流、交易策略网关和审计系统；如果暴露到公网或多团队共享环境，需要按生产化要求继续加固。



## 配套RPC代理的定位

钱包本体是主要开发内容，负责账户、助记词、网络、站点授权、交易确认、本地签名和资产展示。RPC代理只是一个辅助模板，用来解决浏览器环境不适合直接运行 Java SDK、也不适合直接维护 SDK 证书连接细节的问题。

在使用原生 RPC、国密链或未开启 Web3 RPC 的节点时，典型调用链路如下：

```text
DApp 页面
    |
    v
window.fisco
    |
    v
FISCO BCOS Wallet 浏览器扩展
    |
    v
HTTP JSON-RPC
    |
    v
fisco-bcos-wallet-proxy
    |
    v
FISCO BCOS Java SDK
    |
    v
FISCO BCOS 节点
```

在这个链路中，职责边界应当保持清晰：

- **钱包**：管理用户账户、保存加密 Vault、按站点授权、展示交易确认窗口，并在扩展本地完成交易签名；
- **RPC代理**：维护节点 SDK 连接、route 与 group 映射、标准/国密配置、RPC 方法白名单和请求限制；
- **DApp**：负责业务页面、合约参数组装和交易发起，不直接接触用户私钥。

也就是说，RPC代理可以帮助钱包连到 FISCO BCOS 原生节点，但不应该接管钱包的签名职责。`sendTransaction` 等写链请求应当只转发钱包已经签名好的原始交易；RPC代理不接收助记词、不保存用户私钥，也不提供中心化代签能力。

### RPC代理的基础安全设计

作为最小可运行模板，RPC代理适合本地开发、演示环境和受控测试环境。它内置以下基础防护思路：

- 通过 RPC 方法白名单限制可调用接口，避免浏览器侧任意透传节点能力；
- 按 route 隔离不同链、群组、密码体系、SDK TOML 和证书目录；
- 限制请求体大小和 JSON-RPC batch 数量，降低异常大请求对服务的影响；
- 对 JSON-RPC 请求做基础格式校验，包括 `jsonrpc`、`method`、`params` 和 `id`；
- SDK 客户端按 route 懒加载，单条链配置异常不影响整个服务启动；
- 上游 SDK 异常详情写入服务端日志，对前端返回收敛后的错误信息；
- 证书、账户文件和本地环境覆盖配置不提交到代码仓库。

这些能力只能算是基础防线。它们能让模板更适合演示交互数据格式和二次开发，但还不能直接等同于生产级网关。

### RPC代理的生产化加固方向

如果RPC代理要部署到公网、生产环境或多团队共享环境，建议继续补充以下能力：

- 增加 API Key、JWT、OAuth2、mTLS 或统一网关鉴权；
- 配置 CORS origin 白名单、IP 白名单、内网安全组或 VPN；
- 做读写 route 分离，只读 route 开放查询类 RPC，写链 route 单独控制 `sendTransaction`；
- 对写链请求增加交易策略校验，例如目标合约地址、函数选择器、from 地址、value、gas/limit 等；
- 按 IP、route、DApp 或账户做限流、并发控制和失败熔断；
- 增加审计日志，记录来源、route、method、耗时、错误码和交易哈希，同时避免记录私钥、签名材料和敏感业务参数；
- 通过挂载目录、配置中心或密钥管理系统注入证书和账户材料，避免进入镜像和仓库；
- 收敛 Actuator 暴露范围，对健康检查以外的管理端点增加认证；
- 通过 Nginx、网关或负载均衡统一配置 HTTPS、超时、请求大小和安全响应头。

因此，现有的RPC代理仓库更适合作为“如何接入 FISCO BCOS 节点”的基础模板，而钱包本体才是用户资产与签名安全的主体实现。
